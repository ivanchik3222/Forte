# План подключения бэкенда Forte Control

Цель первого релиза — подключить существующий интерфейс к реальному API: вход, сохранение видео, история, просмотр записей, камеры, оповещения, отметки просмотра и сводка. ИИ-анализ, распознавание нарушений и подключение видеопотоков камер в этот релиз не входят.

Исходный анализ выполнен 17 октября 2026 года. Раздел 1 описывает состояние до реализации. Этапы 1–5 реализованы; этап 6 реализован в коде и автоматических проверках, фактический production-запуск и визуальная проверка браузером остаются эксплуатационными проверками. Актуальный контракт — [API_CONTRACT.md](API_CONTRACT.md), запуск и переход с прежней БД — [RUNBOOK.md](RUNBOOK.md).

Реализация сохраняет существующий Flask, общий UI-компонент истории и отдельный демонстрационный интерфейс. Рабочие экраны расположены в `frontend/src/features/workspace/`. Модели пока оставлены в одном `backend/models.py`: разбиение на пакет не требуется для текущего объёма. Идемпотентные ключи сохраняются на срок жизни записи. Восстановление короткой ссылки на видео выполняется явной кнопкой в карточке.

## 1. Что уже есть

Приложение предназначено для контроля кассовых операций. В нём два независимых процесса: проверка загруженной записи и просмотр событий от камер. Их нельзя объединять в одну историю или один счётчик.

| Экран или функция | Текущее поведение | Что нужно подключить |
| --- | --- | --- |
| Главная `/` | Информационная страница, переход в кабинет | Остаётся публичной |
| Вход и профиль | LoginPanel вызывает реальный `/api/auth/login`; пользователь и JWT хранятся в памяти | Восстановление сессии, refresh, выход, защита рабочего режима |
| Обзор `/workspace` | Считает сегодняшние события и просмотры из Zustand, показывает камеры и последние загрузки | Серверная сводка, реальные списки, пустые состояния |
| Новая проверка | Выбор файла и drag-and-drop, MOV/MP4/WebM до 1 ГиБ | Приём файла, проверка содержимого, запись в БД и хранилище |
| История `/history` | Поиск по имени, фильтры, сортировка; записи только в памяти | Серверные фильтры, пагинация и постоянная история |
| Карточка `/analysis/:id` | Видео из object URL, таймкоды, кадры, нормативные ссылки, JSON, отмена и повтор | Получение записи по ID, защищённое видео, новый статус без анализа |
| Оповещения `/notifications` | Фильтры по дню, камере и просмотру; просмотр одного или текущего списка | Постоянные события и персональные отметки просмотра |
| Нормативная база `/sources` | Один источник из `data/demo.ts` | Чтение справочника из API, без автоматической правовой оценки |
| Настройки `/settings` | Демо/API, API-ключ в памяти, адрес из переменной сборки | Состояние нашего API и доступные возможности, без обязательного ML-ключа |

Основные файлы фронтенда: `frontend/src/App.tsx`, `pages/OverviewPage.tsx`, `pages/NotificationsPage.tsx`, `store/useAnalysisStore.ts`, `store/useNotificationStore.ts`, `store/useAuthStore.ts`, `features/analysis/`, `features/notifications/`, `api/client.ts`.

Бэкенд уже содержит Flask, SQLAlchemy, Flask-Migrate, JWT, модель User, auth/admin endpoints и тесты авторизации. В production Compose предусмотрен PostgreSQL, локально — SQLite. Есть Docker и workflow тестирования и деплоя. Переписывать этот фундамент не требуется.

### Разрывы интеграции

- Фронтенд вызывает `/api/v1/analyze` и `/api/v1/jobs/:id` с `X-API-Key`, но таких маршрутов в текущем Flask нет. Вход использует отдельный JWT-контур, который не связан с загрузками.
- `records` и `alerts` стартуют с демоданных. Реальная история, камеры и отметки просмотра не загружаются с сервера.
- Прямой переход к карточке после обновления страницы не восстанавливает её: `App.tsx` ищет запись только в массиве store.
- `retry()` использует объект File; если его нет, `start()` выбирает деморежим. После появления постоянной истории этот путь нужно заменить, иначе повтор может неожиданно стать демонстрацией.
- Общий `apiRequest` выставляет JSON Content-Type для любого body. Для FormData это необходимо исправить: boundary устанавливает браузер.
- Текущий JobResponse допускает только processing/failed/done. Статус сохранённого, но не проанализированного видео отсутствует. В карточке и StatusBadge нужна отдельная ветка, иначе новый статус попадёт в неподходящий экран результата.
- `cancel()` прекращает только браузерные запросы. Он не отменяет серверную работу.
- `connection: connected` сейчас подписан как подключение потока камер. Доступность Flask не означает наличие наблюдения или анализа.
- В `create_app()` вызывается `db.create_all()`, каталога миграций нет. Часть обработчиков ошибок и CLI зарегистрирована на глобальном app, а не внутри фабрики.
- У сервера пока нет лимита загрузок и постоянного media volume.

## 2. Поведение версии без ИИ

Пользователь входит, выбирает видео, отправляет его на сервер и получает постоянную запись с серверным UUID. После сохранения видит «Видео сохранено. Анализ пока недоступен», может открыть видео, найти его в истории и скачать JSON с метаданными. После обновления страницы или перезапуска сервера всё сохраняется.

Для этой версии у записи `status: stored`, `analysis_status: not_requested`, `verdict: null`, `violations: []`. Нулевое число найденных нарушений не показывается как результат проверки. Отсутствие анализа нельзя превращать в `no_violation`, `done` или бесконечный `processing`.

На фронтенде `uploading` и ошибка отправки — локальные состояния до успешного ответа. Постоянная запись создаётся только после проверки и сохранения файла. Если HTTP-ответ потерялся, повтор с тем же ключом идемпотентности возвращает уже созданную запись.

Камеры представлены справочником. Без внешнего источника состояния камера имеет статус `unknown`/«Не подключена», а не `online`. События самостоятельно не генерируются. Пустая реальная лента — нормальное состояние. Для проверки интеграции используется явная dev/test-команда импорта тестовых событий; они помечаются как тестовые и не выдаются за обнаруженные системой нарушения.

Демо остаётся отдельным явным режимом с текущими примерами. Демо и реальные данные не смешиваются, при недоступности API автоматического перехода на демо нет.

## 3. Архитектура

Сохраняем React + TypeScript + Zustand и существующий Flask. Браузер обращается к одному прикладному API. Flask управляет доступом, метаданными, историей и файлами. PostgreSQL хранит структурированные данные, отдельный Docker volume — видео. SQLite остаётся вариантом локальной разработки; миграции и ограничения проверяются также на PostgreSQL.

В первом релизе достаточно синхронного сохранения файла и короткой технической проверки. Redis, Celery, WebSocket и ML-worker не нужны. Когда появится длительная обработка или транскодирование, её следует вынести в отдельный worker с устойчивой очередью задач.

Предлагаемая структура расширений:

```text
backend/
  migrations/
  routes/                 # media, overview, cameras, notifications, sources
  services/               # storage, media, notifications, overview
  models/                 # выделить из models.py с сохранением импортов db и User
  tests/                  # API, доступ, файлы, миграции
frontend/src/
  api/                    # общий клиент, auth и доменные API
  features/analysis/      # серверная запись и отображение stored
  features/notifications/ # загрузка списка, фильтры и отметки
  store/                  # кеш API и состояние интерфейса
```

### Доступ и сессии

Рабочее предположение MVP: одно внутреннее рабочее пространство. Пользователь видит свои загруженные видео; администратор — все. Справочник камер и события общие для активных авторизованных пользователей; отметки просмотра персональные. Если понадобятся разные отделения с изолированным доступом, до их запуска добавляются workspace/branch и членство, а не только фильтр на фронтенде.

Для рабочего кабинета используем JWT существующего auth. Access token держим в памяти, refresh переносим в HttpOnly cookie с Secure в production и защитой от CSRF; точные SameSite/CORS-параметры задаём под фактическое размещение фронта и API. На старте приложение восстанавливает сессию через refresh и `/auth/me`. Добавляем серверный logout и отзыв refresh-сессии. Все доменные запросы проверяют актуальный `is_active`, права на объект и действительность сессии. Публичную регистрацию в production отключаем; аккаунты выдаются администратором.

Единый API-клиент обновляет access один раз при 401, объединяет одновременные refresh-запросы и не зацикливается. На выходе отменяет запросы и очищает кеши, чтобы данные предыдущего аккаунта не оставались на экране.

### Хранение видео

- Принимаем MOV, MP4, WebM, до `1024 * 1024 * 1024` байт на файл. Общий лимит HTTP-body немного больше из-за multipart; точный лимит файла проверяет приложение.
- Проверяем пустой файл, расширение, сигнатуру/контейнер и наличие видеопотока. Для метаданных используем ffprobe с таймаутом; не доверяем MIME и длительности из браузера. Добавляем соответствующий бинарник в Docker.
- Сохраняем потоково во временный файл вне public/static. Имя хранения — случайный UUID, исходное имя — только отображаемые метаданные. Не допускаем пути из пользовательского имени.
- После проверки перемещаем файл и фиксируем запись. При ошибке БД удаляем оставшийся файл; периодическая CLI-команда очищает устаревшие временные и осиротевшие файлы с безопасным периодом ожидания.
- Добавляем `media_data` volume, проверку свободного места, ограничение частоты/числа параллельных загрузок. Согласуем лимиты тела и таймауты с внешним reverse proxy и Gunicorn: текущие 120 секунд могут прерывать медленную отправку 1 ГиБ.
- Для `<video>` выдаём короткоживущий подписанный URL после проверки JWT и владельца. Он ограничен одним файлом и сроком; проверка доступа повторяется при выдаче содержимого. Поддерживаем Range для перемотки. JWT не помещаем в URL, подписанные query-параметры не пишем в access-логи.
- Не скачиваем 1 ГиБ целиком через fetch только ради авторизации плеера. Не обещаем воспроизведение любого MOV: при неподдерживаемом кодеке предлагаем скачать оригинал; транскодирование — отдельный будущий этап.

## 4. Модель данных

| Сущность | Основные поля и ограничения |
| --- | --- |
| User | Существующая модель; роли user/admin, активность |
| AuthSession | user_id, идентификатор/хеш refresh-сессии, expires_at, revoked_at; без хранения исходного токена |
| MediaRecord | UUID, owner_id, original_name, storage_key, size_bytes, content_type, duration_sec nullable, status=stored, analysis_status=not_requested, created_at |
| UploadRequest | owner_id, idempotency_key, request fingerprint, media_id; уникальная пара owner/key, срок хранения |
| Camera | UUID, name, location, status=unknown, last_seen_at nullable, is_active; online только при реальном источнике heartbeat |
| CameraAlert | UUID, camera_id, source, external_event_id nullable, detected_at, type, description, timecode_sec, rule snapshot nullable; дедупликация по source/external_event_id |
| AlertRead | user_id, alert_id, read_at; уникальная пара user/alert, повторная отметка не меняет первое время |
| EvidenceFrame | UUID, alert_id, timestamp_sec, storage_key; изображения хранятся как файлы, а не в списке оповещений |
| RegulatorySource | UUID, title, number, document_date, url, publisher, is_active; без заявления об автоматически проверенной актуальности |

Все времена API — ISO 8601 UTC. День для фильтров и сводки вычисляется в `Asia/Almaty`, как в текущем интерфейсе. Индексы: MediaRecord(owner_id, created_at, id), CameraAlert(camera_id, detected_at, id), AlertRead(user_id, alert_id). Списки имеют стабильную сортировку с ID при одинаковом времени.

Результаты будущего анализа следует выделить в AnalysisJob и AnalysisViolation при подключении ML. В первом релизе не создавать фиктивные задания. Существующий UI-тип Violation временно отображается через адаптер из деталей CameraAlert; тип события не означает подтверждение нарушения человеком.

## 5. Предлагаемый API

Это новый контракт для реализации, а не перечень уже работающих маршрутов. Префикс прикладных данных — `/api/v1`. Существующие auth endpoints остаются под `/api/auth`.

| Метод и путь | Назначение |
| --- | --- |
| GET `/api/v1/capabilities` | Возможности: uploads=true, analysis=false, camera_stream=false, форматы, лимит файла |
| POST `/api/v1/media` | Multipart `file`, заголовок Idempotency-Key; 201 и постоянная запись после сохранения |
| GET `/api/v1/media` | История: search, status, sort, page, per_page; только доступные записи |
| GET `/api/v1/media/{id}` | Метаданные по постоянному ID для прямой ссылки |
| POST `/api/v1/media/{id}/playback-url` | Короткоживущий URL оригинала для видео/скачивания |
| GET `/api/v1/media/{id}/content` | Файл по ограниченной подписи, Range/206 и обработка неверного диапазона |
| GET `/api/v1/media/{id}/report` | JSON из серверных данных, с явным признаком отсутствия анализа |
| GET `/api/v1/overview?date=YYYY-MM-DD` | Сводка за день, непрочитанные, камеры, последние записи |
| GET `/api/v1/cameras` | Список зарегистрированных камер |
| POST/PATCH `/api/v1/cameras[/{id}]` | Создание и редактирование администратором; отдельная UI-админка не обязательна |
| GET `/api/v1/notifications` | date, camera_id, read=all/new/read, page, per_page |
| GET `/api/v1/notifications/{id}` | Детали события, нормативное основание и ссылки на защищённые кадры |
| POST `/api/v1/notifications/read` | `{ids: [...]}`; отметить только переданные доступные события, идемпотентно |
| GET `/api/v1/sources` | Нормативный справочник |
| POST `/api/auth/logout` | Отзыв refresh-сессии и очистка cookie |

Список: `{items, page, per_page, total}`; `per_page` по умолчанию 20, максимум 100. Счётчики рассчитываются по всему соответствующему набору, а не по загруженной странице. Обзор отдельно возвращает `unread_total` для бокового меню и `today_total/today_read/today_unread` для дневной сводки.

Для отметки «Просмотрены» при пагинации MVP обрабатывает только показанные записи и явно пишет «Отметить показанные». Если потребуется весь результат фильтра, это отдельное серверное действие с зафиксированным фильтром и границей времени, чтобы не захватить только что поступившие события.

Пример ответа после загрузки:

```json
{
  "id": "server-generated-uuid",
  "file_name": "cash-desk.mov",
  "file_size": 31457280,
  "created_at": "2026-10-17T10:00:00Z",
  "duration_sec": 82,
  "status": "stored",
  "analysis_status": "not_requested",
  "verdict": null,
  "violations": []
}
```

DTO API использует snake_case; адаптер фронтенда переводит его в camelCase существующих компонентов. Отдельно валидируются ответы API, а не только TypeScript-типы.

Ошибки унифицируются: `{error: {code, message, details?}}`, с обновлением auth-клиента и тестов. Основные ответы: 400/422 — входные данные, 401 — сессия, 403 — роль, 404 — отсутствующий или чужой объект, 409 — конфликт ключа идемпотентности, 413 — размер, 415 — формат, 429 — лимит, 503 — временная недоступность. Временная ошибка polling не стирает ранее загруженный список.

Текущие `/analyze` и `/jobs` пока не используются рабочим фронтом. При выключенном анализе вызов analyze должен явно отвечать `503 analysis_unavailable`, не создавать вечную задачу. Совместимость с контрактом жюри и `X-API-Key` реализуется отдельным адаптером при подключении ML; браузерный кабинет продолжает работать через JWT.

## 6. План реализации

### Этап 1. Контракт и фундамент

1. Зафиксировать DTO и ошибки в `docs/API_CONTRACT.md`, включая stored, nullable verdict, capabilities и правила доступа.
2. Перенести регистрацию error handlers и CLI в фабрику приложения, обеспечить одинаковое поведение test/prod app.
3. Инициализировать Flask-Migrate/Alembic, создать baseline users и миграции новых таблиц. Убрать автоматическое `create_all()` из рабочего старта.
4. Для существующей БД: резервная копия, проверка соответствия baseline, затем stamp только подтверждённой схемы и upgrade. Для пустой БД — upgrade с нуля. Не штамповать непроверенную production-БД.
5. Добавить единый guard активного пользователя и ограничения области доступа.

Готовность: чистые SQLite и PostgreSQL поднимаются миграциями; существующие пользователи сохраняются при переходе; auth-тесты проходят; ошибки фабрики имеют единый формат.

### Этап 2. Сквозной сценарий входа и загрузки

1. Реализовать refresh-cookie, восстановление сессии, logout, CSRF и общий клиент с поддержкой FormData.
2. Реализовать POST media, проверку контейнера, безопасное хранение, идемпотентность, capabilities и media volume.
3. Подключить UploadPanel и useAnalysisStore к JWT API; для рабочего режима убрать обязательный X-API-Key.
4. Добавить stored в DTO, валидаторы, StatusBadge и AnalysisDetail; переименовать действие в «Загрузить видео», показать недоступность анализа.
5. После ответа использовать серверный ID и открыть карточку сохранённой записи.

Готовность: реальный файл проходит от браузера до диска и БД; карточка показывает отсутствие анализа; пустой, слишком большой и поддельный файл отклоняются сервером; повтор запроса не создаёт дубликат.

### Этап 3. Постоянная история и просмотр видео

1. Реализовать списки, детали, поиск, сортировку и пагинацию.
2. Загружать `/analysis/:id` напрямую из API, различать loading, 404 и сетевую ошибку.
3. Реализовать подписанную выдачу оригинала, Range, обновление истёкшей ссылки и серверный JSON-экспорт.
4. Исправить повтор и отмену: до окончания отправки отменяется upload; после сохранения предлагается открыть сохранённую запись. Не называть прекращение HTTP-запроса удалением файла. Потерянный ответ восстанавливается повтором с тем же ключом.
5. Убрать сообщения о хранении истории только во вкладке; освобождать временные object URL. Фильтр «Без анализа» показывается отдельно от будущих verdict-фильтров.

Готовность: после F5, повторного входа и перезапуска контейнера доступны история, карточка, оригинал и экспорт. Другой обычный пользователь не может прочитать запись или получить ссылку на файл.

### Этап 4. Камеры и оповещения

1. Создать справочник камер, API ленты, детали и таблицу AlertRead.
2. Добавить явно вызываемую dev/test-команду импорта событий и кадров, запрещённую в production по умолчанию; production начинается с пустой ленты.
3. Подключить useNotificationStore к API. Для MVP обновлять список и счётчики polling раз в 15 секунд только в активной вкладке; при ошибках применять задержку повторов, после возврата в окно обновлять сразу.
4. Загружать фильтры с сервера. Просмотр подтверждать сервером; при неудаче показывать ошибку, а не оставлять ложную отметку.
5. Отделить доступность API от подключения камер. Добавить unknown и состояние «Источник событий не подключён». Убрать демо-кнопку генерации из рабочего режима.

Готовность: тестовое событие проходит БД → API → интерфейс; повторная доставка не создаёт дубль; отметка сохраняется после F5 и персональна; фильтры по дню и камере согласованы; нет ложных online-камер.

### Этап 5. Обзор, нормативная база и настройки

1. Подключить серверную сводку, счётчики бокового меню и последние записи; обновлять после загрузки и отметки просмотра.
2. Перевести Sources на API. Перенести имеющийся источник как справочную запись без утверждения о проверке редакции или применимости.
3. Настройки показывают доступность сервера и возможностей; выбор демо/рабочего режима не смешивает stores.
4. Обновить подсказки и тексты, обещающие автоматический поиск событий. Рабочий режим явно показывает, что анализ ещё не подключён.

Готовность: все динамические данные кабинета приходят с API, дневные и общие счётчики корректны при пагинации, empty/error/loading состояния различимы.

### Этап 6. Проверка и запуск

1. Добавить интеграционные тесты доменного API: доступ, загрузки, отказ хранилища/БД, идемпотентность, история, Range, фильтры и персональный read.
2. Проверить фронтенд: сессия после F5, истечение access, stored без ложного verdict, прямая ссылка, отказ API без демоподмены, отмена/повтор, logout и смена аккаунта.
3. Проверить PostgreSQL-миграции в CI, frontend unit tests, TypeScript и production build.
4. Обновить README, env examples, Docker, health/readiness checks. Миграции выполнять один раз до запуска нескольких Gunicorn workers.
5. Подготовить резервное копирование БД и media volume как связанного набора; проверить восстановление. Проверить сохранность данных при пересоздании контейнеров и загрузку большого файла через фактический внешний URL.

## 7. Что останется для подключения ИИ

Следующий этап добавит AnalysisJob, очередь и worker, получение исходного файла из storage, обработку queued/processing/done/failed/cancelled, сохранение результатов и кадров, повтор задач и серверную отмену. Ключ ML-сервиса хранится в окружении сервера. Фронтенд вызывает прикладной Flask API, а не ML напрямую.

Подключение RTSP/видеопотоков и автоматические проверки изображения требуют отдельного источника данных. В расширении 0003 реализованы приём проверок камер с TTL и историей интервалов, приём событий с таймкодами и связью с видео, а также API и подключение страниц «Контроль камер» и «Смена за минуту». Правила интеграции приведены в API_CONTRACT.md и RUNBOOK.md. Генерация событий и определение качества изображения не выполняются этим API. Отдельно потребуются подтверждение/отклонение событий человеком, если такой процесс будет нужен: отметка просмотра сейчас не является решением о нарушении.

Приоритет реализации: сначала этапы 1–3 дают полностью работающий путь реального видео. Затем этапы 4–5 подключают остальные экраны; этап 6 завершает проверку и подготовку запуска.

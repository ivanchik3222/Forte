# Локальный анализ видео

Единый справочник для бэкендера в Word: [Forte Control ML API](Forte_Control_ML_API_Reference.docx).
Он объединяет коды действий и объектов, кандидаты правил, текущий контракт кабинета,
пример JSON, состояния задач и ошибки. Версия справочника — 18 октября 2026 года.

## Текущая версия: бинарный результат и доказательства (18.10.2026)

По умолчанию `ML_ENGINE=reviewed_pipeline`, `ML_AUTO_ANALYZE=true`.
Загрузка в кабинете автоматически запускает R3D-кандидаты и локальную Qwen3-VL-4B.
Qwen отдельно описывает действия и проверяет визуальные признаки по реестру РК.
Видео, кадры и описания не передаются облачным моделям.

```bash
ML/.venv/bin/python scripts/run_local_pipeline.py
# frontend в другом терминале: cd frontend && npm start
```

API работает на `127.0.0.1:6767`, frontend — `localhost:3000`.
Скрипт проверяет файлы моделей, применяет миграции, запускает API и worker.
Остановка Ctrl+C завершает оба процесса. `--check` — только проверка наличия.
Логи: `ML/runs/local_service/{api,worker}.log`.

На новом Mac нужны `ML/.venv` с `backend/requirements.txt` и `ML/requirements-mac.txt`,
`ML/.venv-review` с `ML/requirements-review-mac.txt`, ffprobe.
Голова: `ML/deployment/reviewed/bank_only.npz`.
Энкодер: `ML/.venv/bin/python ML/download_models.py --r3d`.
Qwen: `ML/.venv-review/bin/python ML/download_review_model.py --size 4b`.
Инференс офлайн; старые LoRA-адаптеры до исправления DeepStack не применяются.
Полная связка MLX работает на Apple Silicon; Linux Docker сохраняет `objects`.

### Общая семантика веба и API

* `violation`: обнаружены **признаки возможных нарушений**; `violations` непустой.
* `no_violation`: таких признаков в проверенных фрагментах не обнаружено; список пуст.
* `requires_human_review=true` у эпизода не заменяет бинарный вердикт, а обозначает
  рекомендательный характер результата по разделу 7 ТЗ.
* `assessment_coverage=partial` явно показывает неполный анализ. Если ни одно окно
  не проверено и нет валидных нарушений, задача завершается `failed`, а не «чисто».
* Каждый эпизод имеет `type`, `start_sec`, `end_sec`, `timecode_sec`, `description`,
  `visible_fact`, `explanation`, `rule_id`, `rule` и **свои** 1–3 кадра.
* Для `classification_status=grounded` поле `rule` содержит название, пункт, URL,
  редакцию и содержание из локального реестра. Модель не может придумать ссылку.
* Положительный прогноз R3D без нормативного сопоставления сохраняется как
  `classification_status=unclassified`, `rule=null`, `rule_id=null`. Вердикт остаётся
  `violation`: это признаки по обученному бинарному классификатору, а не установленный
  тип. Кадры показывают его интервал/пик, но не объявляются семантическим доказательством
  конкретного правила. **Для таких эпизодов требования к типу и нормативному обоснованию
  ещё не выполнены.** Интерфейс сообщает это явно.
* Кадры выбирает локальная модель для конкретного вывода; backend проверяет индексы,
  границы эпизода, наличие ключевого таймкода среди кадров. У каждого кадра есть
  объяснение. Это проверка связности данных, не гарантия визуальной истинности.

Источники и ограничения: [regulations/README.md](../ML/regulations/README.md).
Новые названия событий не ограничены обучающими классами; проверяется весь кадр
на всех временных окнах, включая окна без R3D-кандидатов. Нормативные основания
ограничены проверенным реестром. Отсутствие бумажного ID/чека само по себе не вывод.

### API жюри — раздел 10 ТЗ

`POST /api/v1/analyze`, multipart `file`, заголовок `X-API-Key` → `202` с `job_id`
и `status=processing`. MOV поддерживается. Idempotency-Key необязателен.
`GET /api/v1/jobs/{job_id}` с тем же ключом → плоский ответ:

```json
{
  "job_id": "…", "status": "done", "verdict": "violation",
  "violations": [{
    "type": "Кассир покинул место до завершения обслуживания",
    "timecode_sec": 8.033,
    "description": "Наблюдаемое действие и его связь с правилом.",
    "evidence_frames": [{"timestamp_sec": 8.033, "image_base64": "/9j/…", "explanation": "Что видно на этом кадре."}],
    "rule": {"title": "НБРК № 231", "section": "22", "url": "https://adilet.zan.kz/rus/docs/V1900019680", "revision": "16.03.2026"}
  }],
  "coverage_status": "done", "decision_scope": "visible_signs_of_possible_violations"
}
```

Пример условный, не результат конкретной записи. JPEG кодируются в base64.
Ошибочный ключ — 401; чужая задача — 404; занятая очередь — 429; движок без
проверки правил — 503. В работе статус `processing`; при техническом сбое `failed`.

`JURY_API_KEY` задаётся окружением, либо `JURY_API_KEY_FILE` указывает на локальный
секретный файл. Скрипт Mac при первом запуске создаёт случайный ключ в
`backend/instance/jury-api-key.txt` (права 0600, исключён из Git). Не добавлять ключ
во frontend, URL, репозиторий или логи. Публичный URL скрипт не публикует.

### Кабинет с JWT

`POST /api/v1/media` сохраняет запись и ставит её в очередь автоматически.
`GET /api/v1/media/{id}/analysis` и `/api/v1/jobs/{job_id}` с JWT возвращают `result`.
Внутри `result.violations[].evidence_frames` — подписанные `image_url` и объяснения.
Внутренние ссылки `evidence[].evidence_index` указывают в общий массив кадров;
индексы перенумеровываются при объединении R3D и Qwen. JSON-экспорт использует тот
же результат. История также получает `verdict` и краткий список нарушений.

`stage`: `finding_events` → `assessing_rules`. Старые движки и сохранённые
результаты могут иметь `requires_review`/`not_performed`; они не переименовываются
в новые вердикты. Для новой оценки нужно загрузить запись заново.

Банковская голова использует исходную камеру 464×848. На других размерах она
отключается (`unsupported_camera`), но полный кадр проверяется Qwen по правилам.
`events` остаётся списком R3D-кандидатов, `observations` — обычными действиями;
Положительные R3D-сигналы без сопоставления отображаются как неклассифицированные.

65,8% development accuracy относится к прежнему бинарному R3D-классификатору,
**не к новой связке нормативной оценки и не к точности Qwen**. Нужна отдельная
оценка итоговых вердиктов, классификации и кадров. Х-16/Х-17 не использовались.
Технические проверки не доказывают точность или соблюдение 5-минутного SLA на всех
видео. Полнота анализа, пропуски между кадрами и перенос на другой ракурс остаются
ограничениями.

## Дополнительный режим YOLO (без нормативного вердикта)

Доступна также обученная YOLO11n: `ML/deployment/cash_detector.pt`, SHA-256 `be1ff4056ffd36fea226fca6c0beb3cbd5f84bfc2bff34a673934e406ba2ec4f`. Веса включены в Git (около 5,5 МиБ), карточка модели, лицензия и атрибуция лежат рядом. Исходные видео, кадры, исследовательские веса, `.env` и ключи в Git не отправляются.

После загрузки записи появился блок «Наблюдения модели»: выбор профиля, запуск, статус очереди, кадры с боксами, интервалы и переход к времени оригинала. Полный JSON скачивается существующей кнопкой. История отличает готовые наблюдения от записей без анализа. Детектор и эвристики движения не обучены определять последовательность кассовых операций. `rules.json` остаётся с выключенными автоматическими правилами.

## Запуск

`docker compose up -d --build` поднимает API, фронтенд и отдельный `ml-worker`. В production используется также `compose.production.yaml`; worker получает тот же PostgreSQL и том видео, что и API. Сборка worker устанавливает CPU PyTorch; локальный CUDA venv сохранён. GPU в Docker этим изменением не настраивается.

Для локального Windows-запуска сначала из корня:

```powershell
ML/.venv/Scripts/python.exe -m pip install -r backend/requirements.txt -r ML/requirements-inference.txt
```

Из папки `backend`:

```powershell
../ML/.venv/Scripts/python.exe -m flask --app app db upgrade
../ML/.venv/Scripts/python.exe -m flask --app app run --port 6767
# В другом терминале, тоже из backend:
../ML/.venv/Scripts/python.exe -m flask --app app analysis-worker
```

В третьем терминале, из `frontend`: `npm.cmd ci`, затем `npm.cmd start`. Перед запуском задайте настройки по `backend/.env.example`; для проверки контейнера при загрузке нужен `ffprobe` в PATH или `FFPROBE_PATH`. `ML/.env` с ключом Roboflow worker не читает. Для новой установки PyTorch сначала выбрать CPU/CUDA по [ML/README.md](../ML/README.md).

Настройки: `ML_ENABLED` (по умолчанию true), `ML_WEIGHTS` (локальный путь, автоматической загрузки нет), `ML_DEVICE` (`cpu` или `0`; локально выбирается CUDA при наличии). `ML_ENABLED=false` отключает постановку задач. Наличие файла весов определяет `capabilities.analysis`; это не проверка здоровья worker. Если worker остановлен, задачи остаются в очереди. Диагностика: `docker compose logs ml-worker`.

## API

### Подробные локальные описания на Mac (дополнительный режим)

`ML_ENGINE=objects` сохраняет действующий YOLO-анализатор. Для офлайн VLM добавлен
режим `ML_ENGINE=dense_vlm`: нужны локальные веса Qwen3-VL и отдельное окружение
`ML/.venv-review` из [CAPTION_MODEL.md](../ML/CAPTION_MODEL.md).
Команды из `backend`, в двух терминалах:

```bash
ML_ENGINE=dense_vlm ../ML/.venv/bin/python -m flask --app app run --port 6767
ML_ENGINE=dense_vlm ../ML/.venv/bin/python -m flask --app app analysis-worker
```

`ML_VLM_PYTHON` задаёт альтернативный путь к локальному Python с MLX.
`ML_VLM_ADAPTER` — необязательный путь к каталогу исследовательского LoRA-адаптера.
По умолчанию адаптер не включается: снижение loss не подтвердило хорошую точность
конкретных действий. Этот режим рассчитан на Apple Silicon; существующий Linux
Docker-worker продолжает использовать YOLO.

VLM запускается из worker отдельным процессом с реальным wall-clock timeout.
В кабинет передаются текст действия, таймкоды и JPEG через существующие подписанные
ссылки. Confidence детектора для VLM равен `null`, боксы не выдумываются.
`coverage_status=partial` и интервалы без результата отображаются явно.
Автоматический юридический вердикт остаётся отключённым; API жюри этим режимом
не реализуется. При смене движка используйте новую запись: существующая очередь
идемпотентна по media_id и хранит ранее полученный результат.

### Контракт кабинета

JSON-запросы используют существующую JWT-сессию и доступ к записи (владелец/администратор).

| Метод | Путь | Результат |
| --- | --- | --- |
| POST | `/api/v1/media/{id}/analyze` | `{camera_profile:"forte_open"|"full_frame"}` → 202 с задачей; повтор → 200 |
| GET | `/api/v1/media/{id}/analysis` | Задача записи или `null` |
| GET | `/api/v1/jobs/{job_id}` | `queued`, `processing`, `done` или `failed` |
| GET | `/api/v1/jobs/{job_id}/evidence/{index}?token=...` | JPEG по подписанной ссылке из результата |
| GET | `/api/v1/media/{id}/report` | Метаданные и полный результат с кадрами, боксами и интервалами |

Завершённая задача содержит `result.verdict="requires_review"`, `violations=[]`, `rule_evaluation="not_performed"`, `frames`, `events`, `evidence_frames`, SHA модели и параметры. `mean_detector_confidence` описывает уверенность детектора, не вероятность нарушения. Отсутствие денег в детекциях означает неизвестную видимость. На карточке записи `verdict` остаётся `null`; `analysis_status` отражает состояние задачи.

`forte_open` требует исходные 464×848 и использует ROI `[0,300,464,610]`; для другой камеры выбирается `full_frame`, качество переноса не проверено. Обработка: реальные PTS, 2 кадра/с, imgsz=640, conf=0.25, NMS IoU=0.7. Эти параметры зафиксированы до прогона всех видео. Верхняя часть кадра в native-профиле не анализируется; шкаф может частично обрезаться.

Задачи хранятся в таблице `analysis_jobs` (миграция `0004`). Один worker держит общий файловый lock на всё время обработки; используется одна загруженная модель. Ограничение очереди — 20 активных задач; 429 требует повторить запрос позже. Для одной записи сохраняется одна задача; запрос другого профиля после успешного анализа возвращает 409. Ошибочную задачу можно повторить. При рестарте старая processing-задача помечается failed после 390 секунд от старта. Внутренний лимит анализа — 300 секунд с проверкой между кадрами. Для очереди и декодирования больших файлов SLA не установлен.

Кадры хранятся в приватном `MEDIA_ROOT/analysis/{job_id}`. Ссылки действуют 15 минут, проверяют доступ и отзыв сессии. На странице есть обновление ссылок. Существующий endpoint `/api/v1/analyze`, предполагавший классификацию нарушений, остаётся недоступным; для наблюдений используется новый контракт выше.

## Проверка исходных видео

Из корня: `ML/.venv/Scripts/python.exe ML/validate_open_integration.py --output ML/runs/open_integration_new`.

Скрипт создаёт отдельную SQLite через миграции, регистрирует локальные файлы с hard links (при недоступности копирует), вызывает настоящий enqueue API, worker с рабочими весами, статус, выдачу JPEG, Range оригинала и экспорт отчёта. Чужая учётная запись не получает задачу. В этом скрипте HTTP-загрузка/ffprobe не проверяются: они проверяются отдельно тестами backend. Все видео проходят inference, включая два дубликата; кэш предсказаний не используется. Это функциональный тест на train/val/test вместе, не независимая оценка точности. Результаты — [ML/OPEN_VALIDATION.md](../ML/OPEN_VALIDATION.md).

В CI добавлен CPU smoke test с настоящими весами на синтетическом видео; тесты API не требуют установки PyTorch. Локальный smoke: `ML/.venv/Scripts/python.exe ML/smoke_inference.py`.

Проверена также настоящая multipart-загрузка `X-1.mov` через Flask test client → ffprobe → очередь → модель → кадры/JSON: 52 кадра, 12 интервалов, без ошибок. Команда: `ML/.venv/Scripts/python.exe ML/validate_open_integration.py --http-upload --limit 1 --ffprobe ML/cache/ffmpeg/ffmpeg-9.0.2-essentials_build/bin/ffprobe.exe --output ML/runs/http_upload_smoke_new`. Для полного HTTP-прогона убрать `--limit 1`. Флаг лимита загрузок изменяется только в изолированном batch-приложении.

Для этой локальной проверки FFmpeg/ffprobe 9.0.2 скачаны в `ML/cache/ffmpeg` из [сборки Gyan](https://www.gyan.dev/ffmpeg/builds/), на которую ссылается [FFmpeg](https://ffmpeg.org/download.html). SHA-256 архива проверен по опубликованному checksum. Кэш в Git не включается. Проверки: 90 backend-тестов и отдельно 3 проверки настоящих MOV/MP4/WebM (первоначально пропущены без ffprobe), 66 frontend-тестов, 25 ML-тестов, TypeScript, production build, CPU inference smoke. Оба Compose-конфига проверены; Docker-контейнеры здесь не запускались, локальный Docker daemon недоступен.

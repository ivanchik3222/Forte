# Сверка с техническим заданием

Источник: локальный `Кейс_ForteBank.docx`, разделы 4, 5, 7, 10 и FAQ. Проверено 17 октября 2026. Исходный документ не изменён и не публикуется в Git.

## Обязательный результат

Финальный ответ содержит один из двух вердиктов: `violation` — «Обнаружены признаки возможных нарушений», `no_violation` — «Нарушение не обнаружено». `requires_review` допустим как внутреннее состояние наблюдений, но не заменяет итог для жюри. Для каждого события нужны тип, конкретный таймкод, описание, 1–3 JPEG-кадра в base64 и связь с правилом/нормативным источником. В одном видео может быть несколько событий.

Требуемый API: `POST /api/v1/analyze` с `X-API-Key` и MOV в multipart-поле `file`; ответ `{job_id}`. `GET /api/v1/jobs/{job_id}` с тем же ключом возвращает `processing|done|failed`. Максимальное время — 5 минут, включая очередь. Веса и обработка локальны; распознавание/идентификация лиц запрещены. Итог описывает признаки возможного нарушения, а не окончательное дисциплинарное заключение.

```json
{
  "job_id": "example",
  "status": "done",
  "verdict": "violation",
  "violations": [{
    "type": "Тип визуального события",
    "timecode_sec": 44.2,
    "description": "Наблюдаемое действие и связь с применимым правилом",
    "evidence_frames": [{"timestamp_sec": 44.2, "image_base64": "<полный JPEG base64>"}],
    "rule": {"title": "Документ", "section": "Пункт", "url": "https://adilet.zan.kz/…", "explanation": "Почему правило применимо"}
  }]
}
```

Это пример формата, не результат текущей модели. В реальном ответе нужны конкретные проверенные тип, описание и источник.

## Исправления и текущая готовность

`backend/services/final_answer.py` проверяет бинарный итог, описание/источник и 1–3 JPEG, выдаёт настоящую base64, требует совпадения таймкода с конкретным кадром. Пустой список объектов без выполненной классификации не преобразуется в `no_violation`.

Добавлен API жюри: `JURY_API_KEY`, `JURY_OWNER_ID` отдельного активного пользователя с ролью user. Ключ не предоставляет доступ к чужим записям. JWT API кабинета сохранён. `queued` при обращении жюри выдаётся как `processing`; итог — на верхнем уровне JSON по ТЗ. Для нового угла загрузка жюри выбирает полный кадр. Настройки `.env` не создавались и ключи не публиковались.

**Остающийся разрыв с ТЗ:** текущая YOLO обучена на пяти классах объектов. Классификация действий и применимости правил, показ удостоверения и колебания именно рук клиента не обучены. В отчёте `classification_complete=false`; API жюри сообщает `failed / classification_not_ready`. Видео с таким ответом не считается успешно обработанным по ТЗ. Сервис ещё не готов к оценке качества жюри. Тест сериализатора с тестовыми событиями не является проверкой точности модели.

## Удостоверение и руки клиента

Это дополнительные требования пользователя; исходное ТЗ не раскрывает список ожидаемых типов событий.

**Удостоверение:** размечать демонстрацию физического документа или телефона кассиру, роли, интервал операции, видимость, отличия от банковской карты/денег/бумаги. Пункт 19(1) Правил № 231 в индексируемой официальной [редакции 13.06.2022](https://zan.gov.kz/api/documents/136659/rus/13.06.2022/download/pdf) предусматривает физический документ или данные сервиса цифровых документов; полная актуальная редакция не получена. Отсутствие видимой пластиковой карточки не доказывает отсутствие идентификации. Реквизиты, подлинность документа и личность человека не распознаются.

**Колебания рук:** анализировать оригинальные кадры, траектории кистей/запястий клиента, компенсировать движение камеры, отличать колебания от пересчёта/жестов/протягивания предмета. Детекции 2 FPS не позволяют установить быстрые колебания. Дополнительное наблюдение с таймкодом само по себе не создаёт нарушение. Эмоции, умысел, опьянение и диагнозы не выводятся.

На странице записи появились отдельные статусы этих проверок. Пока они обозначаются как не выполненные. [Таксономия](../ML/action_taxonomy.json), [критерии](../ML/CRITERIA.md).

## Следующий этап обучения

`ML/prepare_action_review.py` создал `ML/annotations/action_review/tasks.json`: 40 уникальных видео / 42 ID, train=24, val=10, test=6. Подготовлены поля двух проверок, интервалы операций, роли и кадры. Новая разметка не заполнена автоматически; исходная бинарная метка не является истиной для удостоверения или колебаний рук. Train/val/test разделены по исходникам.

После разметки обучить детектор документов/телефонов/отрицательных предметов и временную модель действий, затем классификатор применимых событий. Оценивать бинарный вердикт на видео, precision/recall/F1 событий и точность кадров, отдельно — два новых признака. Слабый бинарный пилот без типа/основания не заменяет этот этап.

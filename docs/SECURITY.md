# Защита Forte Control

Фраза для судей: **«Мы изолировали демостенд, ограничили доступ к видео по отделениям и камерам, защитили администраторов MFA и проверяем это воспроизводимыми тестами: чужие записи недоступны, отозванные ссылки не работают, перебор паролей и повторное использование токенов блокируются».**

Это утверждение о реализованных и проверяемых границах, а не гарантия отсутствия всех уязвимостей и не сертификат соответствия требованиям банка.

## Проверка перед показом

Из корня репозитория:

```sh
python -m pytest backend/tests/test_security.py -v
python -m pytest backend/tests -q
```

Тесты создают отдельную БД и искусственные файлы. Проверяются доступ А/Б к отделениям, прямые ID, кадры и уже подписанные ссылки, сводные счётчики, выдача прав на отдельную камеру, доступ к связанному видео/отчёту, блокировка старого демоаккаунта, MFA и повтор кода, лимиты по IP и аккаунту (включая email/nickname), ротация refresh и отзыв всей сессии при повторе, парольная политика.

Для живого показа используйте два личных аккаунта и искусственную запись: войдите сотрудником А, откройте событие А, попробуйте ID события Б; отзовите доступ А и повторно откройте прежнюю ссылку на кадр. Ожидается 404 без раскрытия существования чужого объекта. После выхода ссылка должна вернуть 401. Не используйте реальные банковские записи для публичного показа.

## Развёртывание

Схема сервера, Docker Compose, workflow и внешний прокси восстановлены без изменений. Используется прежняя инструкция [RUNBOOK.md](RUNBOOK.md), включая существующий путь `/forte`. Новый HTTPS-шлюз не устанавливается. Настройка TLS на действующем сервере этой задачей не выполнена.

Изменения авторизации пока остаются локальными; сервер и рабочая БД не обновлялись. Миграция 0005 отзывает старые сессии, а камеры без назначенных прав доступны только администратору. Перед обновлением потребуется настроить MFA администраторов командой `flask --app app enroll-mfa` в доверенной консоли сервера и назначить доступ сотрудникам.

## Назначение прав через admin API

Запросы требуют access-токен администратора, прошедшего MFA:

1. `POST /api/admin/branches` с `{"name":"Отделение А"}` → `id` отделения.
2. Создайте камеру через `POST /api/v1/cameras`, затем `PUT /api/admin/cameras/{camera_id}/scope` с `{"branch_id":"ID","is_demo":false}`.
3. `PUT /api/admin/users/{user_id}/access` с `{"branch_ids":["ID"],"camera_ids":[]}` полностью заменяет назначения. Пустые списки отзывают доступ. Для доступа только к конкретной камере используйте `camera_ids`.
4. `GET /api/admin/branches` и `GET /api/admin/users/{user_id}/access` позволяют проверить назначения.

Admin — глобальная привилегированная роль. Обычный сотрудник получает объединение назначенных отделений и камер, только для недемонстрационных камер. Списки, события, кадры, мониторинг и сводные счётчики фильтруются на сервере. Права повторно проверяются при открытии подписанной ссылки. Загруженное видео дополнительно требует владения; если оно связано с недоступной камерой, даже владелец не может его открыть. Изменение доступа не может отменить уже скачанную копию или байты уже начавшейся передачи.

## Демонстрационный доступ

В коде демовход отключён по умолчанию. Включение DEMO_MODE допустимо только для отдельной базы с искусственными данными. Развёртывание отдельного демостенда не выполнялось. Демоаккаунт не получает доступ к рабочим камерам.

## Сессии и ограничения

- Access: 15 минут; абсолютный срок серверной сессии/refresh: 12 часов, обновление его не продлевает.
- Refresh одноразовый: атомарная замена JTI в БД; повтор старого токена отзывает всю сессию. Frontend синхронизирует refresh между вкладками через Web Locks и получает актуальный CSRF. В старых браузерах без Web Locks одновременное обновление вкладок может безопасно завершить сессию и потребовать нового входа.
- 10 попыток входа на аккаунт и 60 запросов авторизации на IP за 5 минут, счётчики общие для процессов API. Ограничение аккаунта учитывает оба варианта входа: email и nickname. Фиксированные окна допускают всплеск на границе окна; это не замена сетевой защите от DDoS.
- Новые/изменяемые пароли: 12–128 символов. Старые пароли не меняются автоматически. Администраторам следует сменить старые короткие пароли при переходе.
- TOTP одноразовый, окно допуска ±30 секунд, повтор использованного временного шага блокируется атомарно.

Полный пентест, шифрование всех архивов/дисков, неизменяемый аудит и политика удаления записей остаются отдельными задачами. HTTPS и закрытие портов проверяются на реальном сервере после развёртывания; прохождение Python-тестов само по себе этого не доказывает.

Реализация MFA учитывает [рекомендации PyOTP](https://pyauth.github.io/pyotp/) о защите от повторов и перебора.

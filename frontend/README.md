# Forte Control — frontend

Веб-интерфейс кейса ForteBank Datathon 2026: главная страница проекта и рабочее пространство проверки кассовых операций по видео. React, TypeScript, Tailwind v4, Zustand и React Router. Бэкенд и ML этим изменением не реализуются.

## Запуск

```bash
cd frontend
npm ci
npm start
```

- `http://localhost:3000/` — главная: возможности, пример результата, процесс, ограничения и FAQ.
- `/workspace` — рабочая сводка за день, последние оповещения, камеры и заметная кнопка «Новая проверка». Загрузка открывается в нижней панели.
- `/notifications` — лента событий от камер: день, камера, новые/просмотренные, детали события и отметки просмотра.
- `/monitoring` — качество наблюдения, состояние камер, журнал перерывов и сценарии демо-сбоев.
- `/shift` — подборка до шести эпизодов дня, воспроизведение, исходный контекст и шкала событий с перерывами наблюдения.
- `/history` — поиск, фильтры и сортировка истории.
- `/analysis/:id` — статус, вердикт, видеоплеер, события, кадры и экспорт JSON.
- `/sources` — открытый нормативный источник.
- `/settings` — переключение демо/API и ввод ключа.

Вход через существующий Flask `/api/auth/login` доступен из профиля. Он не обязателен для демо; JWT авторизации и ключ API анализа — разные механизмы. Авторизация не используется как защита страниц прототипа.

Модальные окна загрузки видео, событий с камер, входа, справки и просмотра кадров оформлены как нижние выезжающие панели. Они поддерживают Escape, восстановление фокуса, блокировку фоновой прокрутки и `prefers-reduced-motion`. На мобильном экране история превращается в карточки записей, а боковое меню заменяет плавающая полупрозрачная панель: обзор, события со счётчиком новых, история, правила и настройки. Она учитывает safe area и не перекрывает конец страницы. На десктопе сохраняется боковая навигация.

## Демо

По умолчанию включён демо-режим. Три готовых отчёта и кнопка «Открыть демо» позволяют проверить интерфейс без сервера. В настройках есть пример результата без событий.

При загрузке своего файла в демо содержимое **не анализируется**, файл никуда не отправляется, результат задан заранее. Синтетические демо-иллюстрации не являются доказательствами. Это явно указано в интерфейсе и экспортируемом JSON.

История, объекты файлов, API-ключ и токены живут только в памяти вкладки. Обновление страницы сбрасывает сессию. Внутренняя навигация React Router не сбрасывает её. Постоянное хранение истории требует отдельного серверного API. Не используйте реальные банковские учётные данные для прототипа.

## Подключение анализа

1. Создайте `.env.local` по `.env.example` и задайте `REACT_APP_API_URL` — базовый адрес сервера **без `/api`**. По умолчанию `http://localhost:6767`.
2. Перезапустите dev-сервер или пересоберите production. Адрес встраивается в сборку.
3. В `/settings` выберите «Подключённый сервис», введите ключ команды и сохраните.
4. Загрузите MOV. Интерфейс также принимает MP4/WebM до 200 МБ; поддержку дополнительных форматов должен обеспечить сервер.

Ключ не записывается в localStorage и не встраивается в сборку. Для публичного подключения используйте HTTPS. Сервер должен разрешать origin фронтенда и заголовок `X-API-Key` в CORS.

Контракт из ТЗ:

```text
POST /api/v1/analyze
X-API-Key: <ключ>
Content-Type: multipart/form-data; boundary=<устанавливает браузер>
file: <File>
→ { "job_id": "example-id" }

GET /api/v1/jobs/example-id
X-API-Key: <ключ>
→ { "job_id": "example-id", "status": "processing" }
→ { "job_id": "example-id", "status": "failed", "error": "описание" }
→ { "job_id": "example-id", "status": "done", "verdict": "no_violation", "violations": [] }
```

Для `violation`:

```json
{
  "job_id": "example-id",
  "status": "done",
  "verdict": "violation",
  "violations": [{
    "type": "Название события",
    "timecode_sec": 18.2,
    "description": "Наблюдаемое действие и основания для проверки",
    "evidence_frames": [{ "timestamp_sec": 18.2, "image_base64": "<JPEG base64 без data: префикса>" }],
    "rule": {
      "title": "Название документа",
      "section": "Проверенный пункт или раздел",
      "url": "https://adilet.zan.kz/rus/docs/...",
      "explanation": "Связь наблюдаемого действия с правилом"
    }
  }]
}
```

`rule` — необязательное расширение схемы жюри, необходимое для показа нормативного основания. Без него интерфейс явно сообщает об отсутствии источника. Не подставляйте непроверенные пункты. В `processing` можно дополнительно передать `progress` (0–100) и `stage`. Без прогресса показывается неопределённый индикатор, а не выдуманный процент.

Опрос выполняется раз в 1,8 секунды. Общий лимит ожидания, включая загрузку, — 5 минут. Отмена прерывает запросы браузера; серверная отмена не предусмотрена контрактом. Ошибки сети, ключа, формата ответа, размера файла и timeout показываются явно; автоматического переключения на моки нет.

MOV-контейнер не гарантирует поддержку кодека браузером. При невозможности воспроизведения интерфейс объясняет ситуацию; отправка исходного файла в API и показ JPEG-кадров остаются доступны. Изменение видео и транскодирование не реализуются на фронтенде.

## Оповещения непрерывного мониторинга

События камер и история ручных загрузок — независимые сущности. В демо есть три камеры, четыре события за сегодня и одно за вчера. Кнопка «Показать новое событие» явно имитирует поступление сигнала: добавляет его в начало ленты, возвращает фильтры к сегодняшнему дню и обновляет счётчики. Таймер не создаёт фиктивные события сам по себе.

Открытие деталей помечает событие как просмотренное, но не подтверждает нарушение. Массовое действие относится только к текущему отфильтрованному списку. Дни и время показываются в `Asia/Almaty`. События и отметки просмотра пока хранятся в памяти вкладки.

**Реальный поток камер ещё не подключён:** в исходном API нет контракта непрерывного мониторинга. Фронт подготовлен к нему через `useNotificationStore` и типы `CameraAlert` / `MonitoredCamera`. Бэкенд/ML должны предоставить источник событий (SSE, WebSocket или polling) и хранение истории. На фронте транспорт должен сначала валидировать ответ сервера, затем вызывать:

```ts
const feed = useNotificationStore.getState();
feed.setConnection("connected"); // Убирает демо-события и демо-камеры.
feed.setCameras(cameras); // MonitoredCamera[], mode: "api".
feed.receiveAlert(alert); // CameraAlert, mode: "api"; история и новые события.
// При обрыве соединения:
feed.setConnection("disconnected"); // Сохраняет уже полученные реальные события.
```

Стабильный `id` события используется для дедупликации при повторной доставке; отметка просмотра при обновлении сохраняется. В `CameraAlert` обязательны `id`, `cameraId`, `cameraName`, `location`, `detectedAt` (ISO с часовым поясом), `mode` и `event` (существующий тип `Violation`: описание, таймкод, JPEG-кадры, необязательное нормативное основание). `readAt` — необязательное ISO-время просмотра. В `MonitoredCamera` передаются `id`, `name`, `location`, `status: online | offline`, `mode`. Контракт фронта предложен для интеграции, а не описывает уже существующий endpoint.

Реальному событию без кадров не подставляется демо-изображение. Ключ API ручного анализа и подключение потока камер независимы; переключатель в `/settings` по-прежнему управляет только проверкой загруженных файлов.

## Контроль самого контроля

В `/monitoring` различаются потеря связи (`offline`), закрытый объектив (`occluded`), зависший кадр (`frozen`) и плохой обзор (`poor_visibility`). Последнее — сниженная видимость, а не полный перерыв наблюдения. Журнал показывает интервалы, текущие проблемы, завершённые сбои и фильтры дня/камеры. Обзор кабинета и шкала смены ссылаются на него.

Фронт **не определяет качество изображения самостоятельно**. Для реального режима сервис должен поставлять свежие проверки и историю интервалов. Одного флага `MonitoredCamera.status: online` недостаточно. Отсутствие сигнала, разрыв соединения или проверка старше 90 секунд дают статус «Нет свежих данных», а не зелёное подтверждение наблюдения. Наличие пустого журнала также не означает 100% доступность.

Предложенный контракт через `useNotificationStore`:

```ts
const feed = useNotificationStore.getState();
feed.setConnection("connected"); // Удаляет все демо-события, камеры и данные качества.
feed.setCameras(cameras);
feed.receiveHealthSignal({
  cameraId: "camera-01", mode: "api",
  status: "occluded", // observing | offline | occluded | frozen | poor_visibility
  checkedAt: "2026-10-17T12:10:00+05:00",
});
feed.receiveHealthIncident({
  id: "incident-123", cameraId: "camera-01", mode: "api", kind: "occluded",
  startedAt: "2026-10-17T12:10:00+05:00",
  // endedAt отсутствует, пока проблема не устранена.
});
// После восстановления — обновлённый интервал с тем же id и новый сигнал observing.
feed.receiveHealthIncident({
  id: "incident-123", cameraId: "camera-01", mode: "api", kind: "occluded",
  startedAt: "2026-10-17T12:10:00+05:00", endedAt: "2026-10-17T12:24:00+05:00",
});
feed.receiveHealthSignal({ cameraId: "camera-01", mode: "api", status: "observing", checkedAt: "2026-10-17T12:24:00+05:00" });
```

История сбоев и текущие сигналы независимы: не восстанавливайте текущий статус из старого интервала. Старые сигналы не перезаписывают новые. Повторная доставка открытого интервала не отменяет уже известное окончание. Входные timestamps должны включать часовой пояс и не быть из будущего; транспорт также валидирует серверную схему и авторизацию.

Перерывы обрезаются по выбранному дню в `Asia/Almaty`. Пересечения на одной камере объединяются. Сумма по разным камерам обозначена как **камера·мин**, это не длительность простоя всего отделения. Доли uptime не рассчитываются без полной истории проверок.

В демо раскрывается блок «Проверить сценарий сбоя»: выбрать камеру и проблему → «Показать сбой» → «Восстановить в демо» на карточке камеры. Это меняет статус и создаёт/закрывает интервал в журнале; действие недоступно при реальном подключении. Все данные по-прежнему живут в памяти вкладки.

## Смена за минуту

`/shift` собирает до шести последних событий выбранного дня и камеры, затем показывает их по времени. Каждый эпизод длится до 10 секунд. Есть пауза, предыдущий/следующий эпизод, перемотка фрагмента, список эпизодов и клавиатурно доступная шкала дня, выбирающая ближайшее событие. Смена фильтров или состава подборки останавливает воспроизведение. Автопросмотр не подтверждает нарушение и не меняет отметку просмотра — для неё есть отдельная кнопка.

Для настоящего видео добавьте к `CameraAlert` необязательное поле:

```ts
recording: {
  url: "/api/recordings/camera-01/shift.mp4",
  durationSec: 28800,
}
```

`event.timecode_sec` и `evidence_frames[].timestamp_sec` — смещения **от начала этой записи**, а `detectedAt` — абсолютное время события. Фрагмент начинается за 3 секунды до события и заканчивается через 7 секунд после, с ограничением по фактической длине видео. Таймкод сверяется с метаданными браузера. Панель «Что было до и после» ставит подборку на паузу и открывает исходную запись за 15 секунд до события с обычными контролами видео; можно смотреть дальше и возвращаться к моменту события.

URL должен быть HTTP(S) или путём от корня сайта. Видео должно быть доступно браузеру с поддерживаемым кодеком и возможностью перемотки (Range-запросы); авторизация — cookie или короткоживущий URL. Ключ API анализа не добавляется в URL. Видеомонтаж и новый экспортируемый MP4 на фронте не создаются: плеер проигрывает последовательность фрагментов исходников.

Без видео показываются переданные JPEG-кадры и описание; демо использует явно подписанную синтетическую иллюстрацию. При ошибке видео, неверном таймкоде или отсутствующих кадрах интерфейс сообщает об этом. Реальным данным не подставляется демо-изображение. Шкала дополнительно показывает перерывы и плохую видимость; нейтральный фон не означает подтверждённое наблюдение.

## Проверка и сборка

```bash
CI=true npm test -- --watchAll=false --runInBand
npx tsc --noEmit
npm run build
```

`npm start` генерирует CSS и запускает два наблюдателя. `css:watch` использует `--watch=always`, чтобы работать и без интерактивного stdin. `src/styles/generated.css` и `build/` не коммитятся.

Docker запускается через корневой `compose.yaml`. Существующая настройка nginx `try_files $uri $uri/ /index.html` поддерживает прямое открытие всех маршрутов SPA.

## Дизайн и источники

Фирменный ориентир — [официальный сайт ForteBank](https://forte.kz): логотип, основной цвет `#A31551`, тёмный бордовый `#4A0221`, Open Sans. Учтены локальные материалы `design rules`: единая сетка, визуальная иерархия, свободные отступы, сдержанные тени. Шрифты и изображение включены в сборку; внешние ресурсы при обычной работе не загружаются.

Hero-изображение с объективом и четыре объёмные иллюстрации в палитре бордовый/голубой сгенерированы специально для оформления проекта. Иллюстрации карточек поставляются в WebP, в двух размерах, с отложенной загрузкой и прозрачным фоном. Это декоративный визуал, не кадр видеонаблюдения. Изображение кассы в демо сгенерировано и прямо обозначено как синтетическая иллюстрация.

Голубой орнамент `src/assets/forte-oyu.png` сгенерирован по мотивам парного завитка из [визуальной айдентики ForteBank](https://www.behance.net/gallery/31008311/ForteBank-Visual-Identity). Он используется только как декоративный акцент в завершающем блоке главной, сводке событий и карточке локальной обработки. Для орнамента выделено место вне текста и элементов управления, включая мобильную версию.

Нормативный источник: [постановление Правления НБРК от 29.11.2019 № 231](https://adilet.zan.kz/rus/docs/V1900019680). Фронтенд не выполняет юридическую классификацию. Актуальную редакцию, применимые пункты и сопоставление событий должна проверить команда.

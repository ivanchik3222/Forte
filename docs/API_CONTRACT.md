# Контракт API Forte Control

Реализованная версия без ИИ. Базовый URL задаётся через `REACT_APP_API_URL` **без `/api`**, например `http://localhost:6767` или `https://example.com/forte`. В последнем случае reverse proxy снимает `/forte` перед передачей запроса Flask. Демонстрация без входа не вызывает доменные API; тестовый аккаунт работает с настоящим API.

## Сессии и доступ

- `POST /api/auth/login`, JSON `{identifier,password}` → `{user,access_token,csrf_token}`. Refresh JWT возвращается только в HttpOnly cookie. Регистрация доступна в development/test, отключена в production.
- Быстрый тестовый вход использует тот же endpoint с публичными данными `demo@forte.test` / `ForteDemo2026!`. Пользователь создаётся командой `seed-demo-user` при старте Docker или командой `init-db`, имеет роль `user`. Изменение его профиля, пароля, удаление и повышение до admin возвращают `403 demo_account_shared`; регистрация зарезервированного email — `409 reserved_account`. Данные этого аккаунта общие для всех вошедших в него посетителей.
- `GET /api/auth/session-csrf` с cookie → `{csrf_token}`. Используется после перезагрузки страницы. Разрешён только origin фронтенда; ответ нельзя кешировать.
- `POST /api/auth/refresh` с cookie и `X-CSRF-TOKEN` → `{user,access_token}`.
- `GET /api/auth/me` с Bearer access → `{data:{user}}`.
- `POST /api/auth/logout` с cookie и `X-CSRF-TOKEN` → отзыв серверной сессии, очистка cookie. Старые access-токены и ссылки этой сессии перестают работать.

Доменные endpoints требуют `Authorization: Bearer <access_token>`, кроме выдачи содержимого по подписи. Сервер проверяет активность пользователя и сессии при каждом запросе. Видео доступны владельцу и текущему администратору. Камеры, события и источники общие для одного рабочего пространства; read-отметки персональные. Изоляция разных организаций/отделений пока не реализована.

Для разных origins клиент передаёт `credentials: include`. Настройки: `CORS_ORIGINS`, `COOKIE_SECURE`, `COOKIE_SAMESITE`, `AUTH_COOKIE_PATH`. Для публичного префикса `/forte` cookie path должен быть `/forte/api/auth`. В production используется HTTPS и Secure cookie. Разные сайты требуют SameSite=None и Secure; развёртывание на одном сайте предпочтительнее из-за ограничений сторонних cookies браузерами.

## Общие правила

Ошибки: `{error:{code,message}}`. HTTP-коды: 400 — формат запроса/параметры, 401 — сессия, 403 — права/origin, 404 — отсутствующий или чужой объект, 409 — конфликт ключа, 413 — размер, 415 — формат видео, 422 — поля, 429 — лимит, 500 — внутренняя ошибка, 503 — хранилище/ffprobe/анализ недоступны.

Списки: `{items,page,per_page,total}`. `page >= 1`, `per_page` по умолчанию 20, максимум 100. Номер страницы вне диапазона возвращает пустой items. Имена JSON-полей — snake_case. Время — ISO 8601 с UTC-смещением. День событий — `Asia/Almaty`.

## Видео

| Метод и путь | Вход и результат |
| --- | --- |
| GET `/api/v1/capabilities` | `analysis` зависит от наличия локальной модели; `analysis_kind="object_observations"`, `automatic_violation_detection=false`; остальные возможности загрузки/мониторинга сохранены |
| POST `/api/v1/media` | Multipart, один `file`, обязательный `Idempotency-Key` до 80 букв/цифр/`-`/`_`. 201 для новой записи, 200 для повтора |
| GET `/api/v1/media` | `search` по имени, `status=all|stored`, `sort=newest|oldest`, page/per_page |
| GET `/api/v1/media/{id}` | Одна запись |
| POST `/api/v1/media/{id}/playback-url` | `{url,expires_in:900}`; url относительный от корня API-сервера |
| GET `/api/v1/media/{id}/content?token=...` | Подписанная выдача; Range → 206, неверный диапазон → 416, `download=1` для скачивания |
| GET `/api/v1/media/{id}/report` | JSON метаданных с `notice`, Content-Disposition attachment |
| POST `/api/v1/analyze` | API жюри с `X-API-Key`: MOV в поле `file` → `{job_id}`. Нужны JURY_API_KEY и JURY_OWNER_ID |
| GET `/api/v1/jobs/{job_id}` | С ключом жюри: `processing|done|failed`, бинарный итог и JPEG base64 по ТЗ. С JWT: внутренний DTO задачи |

Запись имеет форму:

```json
{
  "id": "UUID",
  "file_name": "cash.mov",
  "file_size": 31457280,
  "created_at": "2026-10-17T10:00:00+00:00",
  "duration_sec": 82,
  "status": "stored",
  "analysis_status": "not_requested",
  "verdict": null,
  "violations": []
}
```

`duration_sec` может быть null. `status="stored"` означает сохранение файла, `analysis_status` — `not_requested|queued|processing|done|failed`. `verdict=null` и `violations=[]` сохраняются: наблюдения модели не подтверждают нарушение. Контракт задач, результатов и подписанных кадров: [ML_INTEGRATION.md](ML_INTEGRATION.md). Служебные storage_key и owner_id в DTO не раскрываются.

Лимит файла — 200 МиБ; HTTP-body допускает дополнительно 1 МиБ для multipart. Файл проверяется ffprobe по контейнеру и видеопотоку. На пользователя разрешена одна одновременная загрузка и 30 новых записей в час. Повтор ключа сравнивает SHA-256 содержимого и исходного имени; другой файл с тем же ключом → 409. Ключ хранится вместе с записью без автоматического истечения. При потере ответа повторяется тот же ключ. Отмена ожидания в браузере не гарантирует отмену уже сохранённого файла.

Короткая ссылка проверяет подпись, срок, объект, текущую активность владельца сессии и доступ. Она перестаёт работать после logout. В access-логах proxy нельзя сохранять query string с подписью. Исходный JWT в URL не передаётся.

## Камеры и события

| Метод и путь | Вход и результат |
| --- | --- |
| GET `/api/v1/cameras` | Постраничный список `{id,name,location,status,last_seen_at,is_active}` |
| POST `/api/v1/cameras` | Admin: `{name,location,is_active?}` → 201 |
| PATCH `/api/v1/cameras/{id}` | Admin: name/location/is_active → 200. Произвольное выставление online запрещено |
| GET `/api/v1/notifications` | `date=YYYY-MM-DD` (сегодня по умолчанию), `camera_id`, `read=all|new|read`, page/per_page |
| GET `/api/v1/notifications/{id}` | Детали и подписанные URL кадров |
| POST `/api/v1/notifications/read` | `{ids:[...]}`, до 100 ID. Возвращает `{items:[{id,read_at}]}`. Если есть неизвестный ID, весь запрос отклоняется |
| GET `/api/v1/frames/{id}/content?token=...` | JPEG по короткой подписи |

Список уведомлений дополнительно возвращает `counts:{all,new,read}` за выбранный день/камеру, до фильтра read и пагинации. В списках кадры не загружаются; детали возвращают `evidence_frames:[{timestamp_sec,image_url}]`.

Событие: `{id,camera_id,camera_name,location,detected_at,source,read_at,event}`. `event` содержит `type,description,timecode_sec,evidence_frames,rule`; rule nullable, при наличии — `title,section?,url?,explanation?`. `read_at` nullable. `source=test` явно обозначает тестовое событие. Повторная отметка не меняет первое время просмотра. Дедупликация при импорте — source/external_event_id.

Камера без heartbeat имеет `status=unknown`. Непрерывного захвата потока нет. Реальная лента начинается пустой; тестовый импорт выполняется отдельно через CLI и запрещён в production по умолчанию.

## Сводка и источники

- `GET /api/v1/overview?date=YYYY-MM-DD` → `date,today_total,today_read,today_unread,unread_total,camera_total,media_total,recent_alerts,recent_media`. unread_total относится ко всем дням пользователя, media_total — ко всем доступным ему записям. Последние события ограничены 5, видео — 3. Счётчики не зависят от страниц списков.
- `GET /api/v1/sources` → постраничный список `{id,title,number,document_date,url,publisher}`; отсутствующие справочные поля могут быть null.

Фронтенд обновляет сводку и открытую ленту раз в 15 секунд в видимой вкладке; при ошибках увеличивает интервал до 60 секунд. После возврата в окно обновляет сразу. При временной ошибке сохраняет ранее полученные данные и показывает ошибку.

## Контроль наблюдения (миграция 0003)

| Метод и путь | Назначение |
| --- | --- |
| POST `/api/v1/cameras/{id}/health` | Admin: принять реальный результат проверки от коллектора |
| GET `/api/v1/monitoring` | `date`, `camera_id`, `page`, `per_page` (50, максимум 100); камеры, текущие сигналы, журнал и сводка |
| GET `/api/v1/shift` | `date`, `camera_id`; шесть последних событий, камеры и интервалы дня |
| POST `/api/v1/events` | Admin: принять событие с таймкодом, без запуска ИИ |
| PUT `/api/v1/notifications/{id}/recording` | Admin: связать существующее событие с видео, `{media_id}` |

Проверка камеры:

```json
{
  "external_id": "collector-1:camera-1:2026-10-17T07:10:00Z",
  "source": "collector-1",
  "status": "offline",
  "checked_at": "2026-10-17T07:10:00Z"
}
```

Статусы входа: `observing`, `offline`, `occluded`, `frozen`, `poor_visibility`. `observing` означает проверенное получение изображения и видимость зоны, а не просто доступный TCP-порт. Источник должен проверять поток и изображение сам; Flask не делает таких проверок и не вызывает ML. JWT должен принадлежать действующему admin. Используйте отдельный аккаунт интеграции и обновляйте его сессию обычным auth API. Раздельной роли коллектора пока нет.

`external_id` до 120 символов уникален внутри камеры, `source` до 80. Идентичный повтор → 200 с прежним ID; новое сообщение → 201; тот же ID с другими полями → 409. Дата требует часового пояса и не может быть в будущем. Новые проверки принимаются строго по возрастанию времени; опоздавшие или с тем же временем → 409 `out_of_order` (идентичный повтор прежнего ID допустим). Неактивная камера отклоняет новые сообщения. На камеру нужен один упорядоченный поток проверок. Запись и переходы интервалов сериализованы блокировкой строки камеры в БД.

Проверка действительна 90 секунд. Повторные проверки одного состояния продлевают один интервал. Изменение состояния закрывает его. После истечения TTL текущий статус становится `unknown`, известный сбой закрывается на границе TTL, а дальше идёт отдельный интервал отсутствия проверок. Это вычисляется и без фоновой задачи; следующая проверка закрепляет этот пробел в БД. `unknown` не означает отключённую камеру. До первой проверки история доступности неизвестна и не включается в минуты.

Ответ monitoring: `{date,as_of,ttl_seconds:90,cameras,signals,incidents,summary}`. `cameras` — полный справочник рабочего пространства; signals и сводка относятся к camera_id, если выбран. `incidents` — `{items,page,per_page,total}`. Для совместимости с компонентами фронтенда вложенные сигналы и интервалы используют camelCase:

```json
{
  "signals": {"camera-id":{"cameraId":"camera-id","mode":"api","status":"offline","checkedAt":"2026-10-17T07:10:00Z","source":"collector-1"}},
  "incidents": {"items":[{"id":"interval-id","cameraId":"camera-id","mode":"api","kind":"offline","startedAt":"2026-10-17T07:10:00Z","endedAt":"2026-10-17T07:11:30Z","duration_sec":90}],"page":1,"per_page":50,"total":1},
  "summary": {"problems":0,"unknown":1,"unavailable_minutes":1.5,"unknown_minutes":2,"degraded_minutes":0}
}
```

`problems` и `unknown` — состояние камер сейчас; минуты — за выбранный день по Астане. Интервалы обрезаны границами дня и текущим временем, endedAt=null только для продолжающегося интервала. `unavailable_minutes` включает offline/occluded/frozen; poor_visibility и unknown подсчитываются отдельно. По одной камере интервалы не пересекаются; параллельные сбои разных камер суммируются как камера·мин. Сводка не зависит от страницы журнала. `/overview` дополнен той же `monitoring_summary`, `/cameras` вычисляет актуальный status и добавляет `health_status`.

## События и обзор смены

Создание события:

```json
{
  "camera_id": "UUID камеры",
  "source": "manual",
  "external_event_id": "operator-mark-001",
  "detected_at": "2026-10-17T07:10:00Z",
  "type": "Эпизод для проверки",
  "description": "Описание специалиста или подключённого источника",
  "timecode_sec": 30,
  "media_id": "UUID загруженной записи"
}
```

`media_id` необязателен; `timecode_sec` — смещение от начала именно этой записи (по умолчанию 0). При наличии записи таймкод должен быть меньше известной длительности; NaN, Infinity, отрицательные числа и boolean отклоняются. detected_at — реальное время эпизода с часовым поясом, не в будущем. Дедупликация по source/external_event_id: 201 при создании, 200 при идентичном повторе, 409 при расхождении. `source=manual` отображается как отметка специалиста; `test` — как тестовое событие и запрещён в production без ALLOW_TEST_EVENTS. Для внешнего источника задаётся его имя. rule и кадры этим endpoint не генерируются. Подмена полей и внешние URL видеозаписи не принимаются.

Все DTO событий дополнены `recording:null|{media_id,duration_sec}`. Поле заполнено только при доступе пользователя к файлу. Общедоступное событие не открывает чужую личную загрузку: другой пользователь видит описание, а запись доступна владельцу и admin. `PUT .../recording` связывает или заменяет запись существующего события без изменения его таймкода. Повторный импорт первоначального события после замены этой связи может вернуть 409; замену связи следует считать отдельным изменением.

Ответ `/shift`: `{date,total,selection:"latest_six",max_duration_sec,episodes,cameras,incidents,monitoring_summary,as_of}`. total учитывает все события выбранного дня/камеры. Берутся шесть последних по detected_at/id, затем выдаются по возрастанию времени. Это подборка последних событий, не рейтинг важности. В episodes включены доступные кадры по подписанным URL и персональный read_at. incidents содержит все интервалы выбранного дня/камеры для шкалы, без пагинации; для большого числа камер используйте фильтр.

При выборе эпизода и открытии контекста браузер запрашивает POST `/media/{id}/playback-url`. Сервер выдаёт исходный файл с Range. Короткий фрагмент ограничен `[max(0,timecode-3),min(duration,timecode+7)]`; контекст начинается за 15 секунд до события и позволяет посмотреть всю запись. При истечении подписи можно обновить ссылку в плеере. Без доступного видео показываются только переданные кадры/описание; синтетические изображения в рабочем режиме отсутствуют. Физический монтаж нового MP4 не выполняется. Просмотр не ставит read автоматически: отдельная кнопка сохраняет его через существующий API и подтверждает только после успеха.
